# Evidence lab: context for Claude

This repository, `Depthmark-Lab/test-evidences`, runs the evidence signing kit on real infrastructure: the self-hosted runners on the Talos cluster and the homelab Vault, whose Transit engine holds the private keys. The kit itself was designed for a bank in `~/code/evidence-kit-v2` (fake names, `acme-bank`); this is a working copy of `evidence-kit/` from there, adapted to the lab. Port fixes in both directions.

## The rule that always holds: evidence logic never touches JFrog or Vault

Collectors and evidence processing hold the business logic: which facts to gather, how to shape them into a predicate, whether the result is `pass` or `fail`, and whether the predicate matches its schema. They know nothing about where evidence is signed or stored. They hand over a predicate and stop.

- `signing.py` is the only module that talks to Vault or JFrog. `cli.py` is the only place where it meets the evidence logic.
- Collectors, `evidence_sdk.py`, `collection.py`, `schema.py` and `core.py` never import `signing.py`, directly or through another module. Neither does `verification.py`, since a verifier needs public keys only, nor `display.py`, which shows predicates in logs and step summaries. `cli.py check` fails if one does, and CI runs it on every push.
- A collector's secrets reach it as values, through a resolver that `cli.py` supplies: Vault in `run`, the environment in `collect`. The collector cannot tell which.
- `signing.py` never interprets a predicate. With JFrog it only checks that JFrog's statement carries the predicate unchanged; with the file store it builds the same statement itself.
- The catalog is where the two sides meet in data. Only `cli.py` and `signing.py` read `family` and the secret `path`; `verification.py` reads `family` to check which key may sign a type.
- `collect` runs every evidence type with a settings file that has no Vault or JFrog section, and so does `verify`. Tests do exactly that, so the split cannot quietly erode.

Why: evidence types change often and have many owners, while the signing path is the trust boundary and changes rarely. Replacing Vault or JFrog, or running evidence with no backend at all, must not touch a collector.

When you add or change code, keep it on its side. If evidence logic seems to need something from Vault or JFrog, pass the value in from `cli.py` instead.

## How the lab signs

- **Two jobs in `.github/workflows/evidence.yml`.** `collect` runs the collectors and scanners without `id-token` permission. `sign` checks each predicate against its schema and its commit again, then signs. A scanner can therefore never request a signing token. `tests/test_kit.py` (`WorkflowTest`) fails if the collect job gains `id-token` or the sign job installs scanners.
- **One call per evidence type.** `evidence.yml` takes a single `type`, and refuses a list. Callers call it from a matrix with `fail-fast: false`, so each type has its own collect and sign jobs, log and summary, a type that fails stops no other, and the collect job installs only the scanner its type calls (`install-scanners.sh <bin> trufflehog`). Each call's artifacts carry the type, `evidence-predicates-<type>` and `evidence-envelopes-<type>`, so the calls of one run never overwrite each other's; `verify` downloads `evidence-envelopes-*` with `merge-multiple`, and `cli.py verify` also reads subfolders, as `gh run download` makes one per artifact. The demo's build job turns its comma-separated input into the matrix's JSON list, since expressions cannot split.
- **Store `file`, no JFrog.** `signing.envelope` builds the in-toto v1 statement JFrog would prepare (subject named by `subject-repo-path`, pinned by SHA-256), signs its DSSE encoding with Transit, and `cli.py` writes `<type>.dsse.json`. The workflow uploads each as the artifact `evidence-envelopes-<type>`. The JFrog store is still there and still tested.
- **`verify` plays JFrog's part.** It checks each envelope with the PEM files in `trusted-keys/` only, never asking Vault, and refuses a key whose family or tier does not match the evidence type in the catalog, so the squads' self key cannot vouch for a scan. RSA verification is pure Python and tested against openssl.
- **Predicates go from collect to sign by artifact id**, the one collect's upload returned, never by name: a caller job of the same run could upload its own `evidence-predicates-<type>`. `WorkflowTest` checks it.
- **Evidence about the squad's build** (`test-results`, `provenance`) is signed with the `build` family. The squad's job builds and tests with its own flags and uploads the deployable and its JUnit XML; `evidence.yml` takes them as `subject-artifact` and `reports-artifact`. It never runs squad code. With `subject-artifact` it hashes the file itself and binds every statement to that SHA-256, `sca` scans the file (`sca` v2, `file:`), and `provenance` is allowed; without it, `provenance` is refused. A caller's `test-reports` parameter is refused, so `test-results` reads what the build uploaded. `WorkflowTest` runs those step scripts with bash.
- **What a run shows.** Each step of `evidence.yml` and the sample workflows has an icon. The collect job's summary gives the subject (its SHA-256, and whether the platform computed it), the scanner versions and a table of the evidence; sign adds the key per type; verify adds each verified statement, folded. `display.py` writes those tables: an icon per status and result, and one line of facts per type, with a fallback to the predicate's `summary` counts for a type it does not know. Squads write some of what predicates hold, so every value is escaped as Markdown, and the shell steps strip Markdown from the names callers pass.
- **The sign log follows Vault step by step.** `signing.Vault` prints each step as it happens: the identity token's claims that the roles bind or record (`signing.CLAIMS`, decoded, never verified: Vault verifies), the login with the role, the token type, TTL and policies Vault returned, the Transit key, algorithm, byte count and SHA-256 of what it signs, then the key version and signature size, each with Vault's `request_id` (in Vault's audit log too) and the time it took. A refusal prints a `⛔` line with Vault's answer, after the claims it refused. The identity token and Vault's token are masked and never printed. `Vault.trail` keeps the same facts, and `display.transit` adds them to the summary as "🔐 How Vault Transit signed", as plain data from `cli.py`, so `display.py` still never reaches `signing.py`.
- **GitHub's attestation, `provenance-attestation`.** `evidence.yml` has a third job, `attest`, for this type only: it downloads and hashes the subject, then `actions/attest-build-provenance` (pinned) has GitHub sign SLSA provenance for it with Sigstore and store it. It holds `id-token: write` and `attestations: write` and runs nothing of the kit's; `WorkflowTest` checks it. `collect` needs `attest` and runs when it succeeded or was skipped; `sign` therefore states its status explicitly, since the default `success()` skips a job whenever an ancestor was skipped. Every caller grants `attestations: write`, whatever its type: GitHub checks a called workflow's permissions before any job runs. The collector runs a pinned `gh attestation verify` with `--signer-workflow` set to `evidence.yml` and `--source-digest` to the commit, both set by `evidence.yml` and refused from callers. "No attestations found" or a 404 is a signed `fail`; any other verification failure is an error, so nothing is signed. Its recording (`tests/scanners/gh-attestation.json`) verifies GitHub CLI's own release archive, since this repository can hold no attestation: GitHub's attestations API answers 404 for a private repository on the Free plan (checked 2026-11-18), so on this repository the `attest` job fails and the `hello-*` runs fail at that type.
- **Called from other repositories.** Every kit checkout, in `evidence.yml` and `verify.yml`, takes `job.workflow_repository` at `job.workflow_sha`: the called workflow's own commit, which is the `job_workflow_ref` Vault trusts. `github.workflow_sha` is the caller's commit, so it never appears there; `WorkflowTest` checks both. So a branch, a tag or a commit of `evidence.yml` always runs its own kit, from this repository or another one, and nothing needs rewriting at release. A caller elsewhere needs this repository to be public, since its token can read nothing else, and verifies with `verify.yml` at the same ref: it hashes the artifact itself and runs `cli.py verify` with the kit's `trusted-keys/`. GitHub's attestation lands on the caller's repository, so a public caller has one on the Free plan. The first such caller is `Depthmark-Lab/hello-world` (public, Go), whose `evidence.yml` builds the binary on GitHub's runners and calls both at `feature/external-consumer` with `runs-on: ["self-hosted", "talos"]`, so its platform jobs run in the runner group `rg-talos` (1Gi runners): those labels match the lab's runners too, but `rg-talos-lab` admits this repository only. Each group admits only the workflows it lists, each at an exact ref (no wildcards; a workflow that is not reusable can only be pinned to a branch): `rg-talos-lab` this repository's workflows at `main` and at the test branches Vault trusts, `rg-talos` the platform's `evidence.yml` and `verify.yml` at those refs and nothing of a caller's own, so a fork's own jobs never reach a Talos runner. A new test branch goes into Vault's roles and both lists. Every job here runs on the Talos runners, inside the homelab, so no workflow here may start on an event a fork can cause either: `WorkflowTest` allows only `push`, `workflow_dispatch`, `workflow_call` and `schedule`. actionlint 1.7.12 does not know the `job.workflow_*` properties yet, so `.github/actionlint.yaml` ignores those two messages in the two files; in a worktree, pass it with `-config-file`.
- **Standard predicate types.** A catalog entry may map a version to another standard's predicateType (`"predicateTypes": {"v1": "https://slsa.dev/provenance/v1"}`); every other version is `<predicateBase>/<type>/<version>`. `core.predicate_type` and `core.evidence_type` are the two directions, shared by `cli.py` and `verification.py`.
- **Keys:** Transit mount `transit-evidence`, one non-exportable RSA 2048 key per family and tier: `evd-scan-lab`, `evd-approval-lab`, `evd-self-lab`, `evd-build-lab`. The key id is `<key>-v<version>`, plus `;PS256` for PSS.
- **Trust:** Vault JWT roles `evidence-<family>-lab` on the `github-actions` mount bind `job_workflow_ref` to `evidence.yml` on `main`, `runner_environment` to `self-hosted`, and `repository_owner_id` to Depthmark-Lab's `71595780`, so a caller outside the organization is refused even once this repository is public. The sign log prints that claim too (`signing.CLAIMS`). Until the process is hardened, they also accept `feature/vault-transit-signing`, `fix/collect-runner-limits`, `feature/build-evidence` and `feature/external-consumer`, for end-to-end tests. Each role's policy allows `update` on its own key's sign path and nothing else. Tokens are batch tokens, 10 minutes.

## Where things live

| What | Where |
|---|---|
| Kit, workflows, tests | this repository |
| Vault roles and policies | homelab repository, `vault/jwt/evidence-{scan,approval,self,build}-lab/`, applied by the user with `vault/apply.sh` |
| Transit mount and keys | homelab repository, `vault/transit-evidence/bootstrap.sh`, run once by the user; it also exports the public keys |
| Trusted public keys | `trusted-keys/` here, written by that script and committed |
| Runners | homelab repository, `talos/apps/action-runner-controller-dev/gha-runner-scale-set-lab/`: labels `self-hosted, talos, linux, lab`, runner group `rg-talos-lab`. `lab-k8s` shares the first three labels, so always include `lab` |
| Scanners | `scripts/install-scanners.sh`, pinned by version and SHA-256, no root needed: TruffleHog, Grype and gh, which verifies GitHub's attestations. It installs both scanners, or only the tools named |
| Sample squads | `samples/hello-{maven,python,node}`, built by `.github/workflows/hello-*.yml` with their own toolchains: Temurin 25 and the Maven wrapper, Python 3.14, Node 24. JUnit XML they wrote is recorded in `tests/reports/` |

Writing to Vault is always the user's step. Never print secret values: no `vault kv get` without `-field` piped into a consumer, no `env`.

## Facts measured on the runner image

`ghcr.io/actions/actions-runner:2.338.2` (Ubuntu 24.04) has Python 3.12, openssl, curl, tar, sha256sum and git, and runs as uid 1001 without privilege escalation, so no sudo and no apt. TruffleHog 3.99.9 runs under its self-updater even with `--no-update`: a parent that waits and a child that scans, each holding every detector, about 190 to 250 MiB apiece. The collector passes the hidden `--local-dev` flag, which scans in one process, about 250 MiB whatever its `--concurrency`; a test checks the flag. Grype 0.121.0 peaks at about 375 MiB, because the database is always downloaded fresh on ephemeral runners. The lab runner container is limited to 512Mi, shared with the runner's own processes (35Mi when idle). On the runner at 512Mi, all four default types were collected on 2026-11-17 (run 44001716002), `sca` included. Locally the cold `sca` collector was OOM-killed at 384Mi, so the margin is thin: raising the limit to about 1Gi is worth it, but not required.

An OOM kills the whole runner. Kubernetes sets `memory.oom.group`, so when one process passes the container's limit the kernel kills every process in it, the runner included. GitHub then reports only "The self-hosted runner lost communication with the server", about ten minutes later, and the job's log is lost. `talosctl -n <node> dmesg` names the process, and the `depthmark-arc-metrics` app posts a failed "Resource Consumption" check naming the pod. That is how both collect jobs of PR #3 ended on 2026-11-17 (runs 44182399376 and 44182399192): two TruffleHog processes, about 190 and 200 MiB, before `--local-dev`. Run 44001716002 had passed with the same two processes, by luck.

Builds on the runner: the image has no Java, Maven, Node, pip or venv, so squad workflows use `setup-java`, `setup-python` and `setup-node`. It has `unzip`, so the Maven wrapper downloads the `.zip` distribution, which is what `distributionSha256Sum` pins. A Maven build with default JVM settings was OOM-killed at 512Mi during the tests (Maven's JVM plus Surefire's fork); with `JAVA_TOOL_OPTIONS=-XX:+UseSerialGC -XX:TieredStopAtLevel=1 -XX:MaxRAMPercentage=25 -Xss512k` it passed at 512Mi and at 384Mi locally, and at 512Mi on the runner, where its jar had the same SHA-256 as the local build. Node 25 and later need `libatomic.so.1`, which the image lacks and a job cannot install, so `setup-node` fails with exit code 127; the Node sample uses Node 24 until the runner image has `libatomic1`.

Local runs: the Mac runs the amd64 image under emulation, so its memory numbers run high, but a local OOM is not proof of emulation. TruffleHog's local kills at 512Mi were first blamed on it, then happened on the runner too. Build samples in the runner image, not in a toolchain image: the Node sample passed in `node:26` and failed on the runner for a library only the runner image lacks.

Disk: only `/home/runner/_work` is a volume (openebs hostpath, no quota). Everything else the pod writes counts against an ephemeral-storage limit of 4Gi, the buildkit sidecar's limit, which Kubernetes applies to the whole pod. Grype's database takes 3.3 GB, so the collect job sets `GRYPE_DB_CACHE_DIR` and `TMPDIR` under `runner.temp`; the `sca` catalog entry passes `GRYPE_DB_CACHE_DIR` through. Without that, the pod was evicted mid-scan on 2026-11-16 (run 43978188427), and the runner only reports "received a shutdown signal".

## Working on the kit

```
python3 evidence/cli.py check                 # catalog, schemas, examples, lock, store and layering agree
python3 -m unittest discover -s tests -v      # 91 tests against stand-in services, needs openssl and bash
python3 evidence/cli.py list                  # evidence types and their parameters
python3 evidence/cli.py collect --types sca --out /tmp/predicates     # no Vault, no JFrog
python3 evidence/cli.py verify --envelopes /tmp/envelopes --keys trusted-keys
python3 scripts/show-envelopes.py /tmp/envelopes/*.dsse.json      # what they say, after verify
python3 tests/scanners/record.py              # refresh recorded scanner output, needs trufflehog, grype, openssl, gh
```

Python standard library only. Keep it that way in the signing path. Scanners are external programs that collectors call. They are not Python dependencies.
